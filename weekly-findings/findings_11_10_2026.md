# Findings 11-10-2026

# 2026-11-10 发现

This week I confirmed that an authenticated user's chatbot session can be accessed without authentication. For a logged-in user the client uses `cusId` as `uuid`; the server accepts that value from any caller without requiring the account's token. An attacker who knows the `cusId` can read/write that user's chatbot session.

本周我确认了：已登录用户的聊天会话可以在未鉴权的情况下被访问。登录用户的客户端把 `cusId` 当作 `uuid`；服务端接受任何人提交的这个值，不要求账号 token。知道 `cusId` 的攻击者可以读写该用户的聊天会话。

## Unauthenticated access to an authenticated session

## 未鉴权访问已登录用户的会话

The victim is logged in; the attacker is not. The chatbot does not bind the conversation to the authenticated account: for a logged-in user the client uses `cusId` as `uuid`, and the server accepts that value from any caller without requiring the account's token. An attacker who knows the `cusId` can read/write the victim's chatbot session. This is not a "cross-user feature"; it is a missing authentication/authorization binding.

受害者已登录，攻击者未登录。聊天机器人没有把会话绑定到登录账号：登录用户的客户端把 `cusId` 当作 `uuid`，服务端接受任何人提交的这个值，不要求账号 token。知道 `cusId` 的攻击者可以读写受害者的聊天会话。这不是“跨用户功能”，而是缺少鉴权/授权绑定。

## Snowflake ID: predictable identifier

## Snowflake ID：可预测的标识符

`cusId` is a 19-digit Snowflake: `timestamp | worker | sequence`. The format is not the vulnerability. It is a good database key. It is a bad **secret** because it is predictable: the timestamp is recoverable, IDs created around the same time are close, and an attacker can enumerate around a known time.

`cusId` 是 19 位 Snowflake：`timestamp | worker | sequence`。格式本身不是漏洞，作为数据库主键很合适。它不适合当**秘密**，因为它是可预测的：时间戳可以还原，同一时间附近创建的 ID 彼此接近，攻击者可以在已知时间附近枚举。

| Point | Meaning | Why it matters |
|---|---|---|
| Snowflake format | time-ordered, decodable | predictable; fine as a DB key, bad as a secret |
| Missing auth binding | `cusId` accepted without token | the actual vulnerability |

```text
id = (timestamp_ms << 22) | (worker << 12) | sequence

test-account id: 2119...9393
timestamp: 2026-11-09T12:13:50Z
worker: 852
sequence: 1
```

**Bottom line:** Snowflake = predictable identifier; missing auth binding = the vulnerability. The format is not the root cause.

**结论：** Snowflake = 可预测的标识符；缺少鉴权绑定 = 真正的漏洞。格式不是根因。

## Stream takeover

## 流接管

When two SSE connections use the same `uuid`, the most recent one receives the answer; the earlier connection gets nothing. An attacker opens a second connection with the victim's `uuid` and receives the victim's next answer; the victim's UI times out or stays blank. Attacker **3/3**, victim **0/3**.

同一个 `uuid` 打开两条 SSE 连接时，最新建立的那条会收到回答，受害者原来的连接收不到。攻击者用受害者 `uuid` 打开第二条连接，就能拿到受害者下一轮的回答；受害者界面会超时或空白。测试中攻击者 **3/3** 收到回答，受害者 **0/3**。

```text
GET /gw/robot/sse/connect   (victim, x-robot-user: <cusId>)
GET /gw/robot/sse/connect   (attacker, x-robot-user: <same cusId>)
POST /gw/robot/sse/chat     (victim sends a question)
=> attacker stream receives the answer; victim stream receives nothing
```
